# Boat candidate handoff

The Boat adapter is experimental. Provider release qualification is **blocked**:
the disposable live fork returned HTTP 409 without a confirmed child identity.
Its creation intent remains unresolved. Do not treat passing offline tests,
completed deletion of known machines, or zero active machines as resolution of
that intent. No provider support or registry publication is declared here.

This page describes what a consumer can evaluate from the private candidate and
what must be resolved before release. Test logs and redacted API results belong
in the linked PRs, not in the package documentation.

## Cleanup and the remaining gate

Each confirmed disposable machine has a matching completed native deletion job.
The unresolved fork has an intent but no confirmed native ID. Its report therefore
retains `cleanupVerified: false` and `qualification: unverified`, even though a
subsequent read-only account check reported zero active machines. That count does
not rule out stopped resources or establish fork outcome.

The [live runner contract](live-verification.md) covers machine, snapshot and
content-record cleanup under the pinned native deletion contract. It does not
prove physical erasure, deletion of independent saved artifacts or zero billing.
Raw private inventories, native IDs, account data and credentials must stay
outside the checkout and PR evidence.

Before removing the release gate:

1. Obtain authoritative read-only/provider-assisted resolution of the pending
   fork intent. Never replay a mutation as lookup, guess targets by name, or
   scan-delete account resources. Record the resolution in private inventory and
   publish only redacted reviewer-accessible proof.
2. Reconcile the remaining machine/start/time/dollar allowance before another
   disposable run. Prior approval is not permission to exceed its cumulative
   envelope, reset counts, or continue while an intent is unresolved.
3. Verify the required fork-copy, file-delete and stop/resume behavior, or make an
   explicit reviewed scope/capability decision. Do not relabel offline coverage
   as live coverage. Resolve every owned creation intent and verify native cleanup.
4. Recheck the actual candidate commit, packed consumer, runtime and UbiCloud
   runner evidence, then complete independent acceptance review. Provider release
   and registry publication remain separate owner decisions.

## Evaluate a packed candidate

From a clean committed checkout, use the existing candidate command with a new
absolute output directory outside the repository:

```sh
pnpm build:lib
pnpm release:candidate /absolute/new/candidate-directory
```

The command packs the existing artifact allowlist and writes `candidate.json`
and `SHA256SUMS` beside the tarball. It refuses dirty source, an output inside the
checkout, or an existing output directory. Keep these generated files outside
source control. Compare their source commit and lockfile digest to the reviewed
commit and verify the tarball SHA-256. The JSON metadata is unsigned; it is not a
provenance attestation or proof that a registry release exists.

Install the actual tarball in a fresh consumer, alongside compatible Convex and
the exact SDK when evaluating Boat:

```sh
pnpm add /absolute/path/to/candidate.tgz convex@1.49.0 @boatdev/sdk@1.13.0
```

Use the [checked authenticated host guide](guide.md) to mount the component and
configure existing authorized bindings. Imports of the Boat entry are server-only;
a successful import does not grant application authorization. Keep the provider
key in server deployment configuration as described in [setup](setup.md).

`pnpm test:package` already installs a packed artifact into an isolated fresh
consumer, verifies core imports without the SDK, then installs the exact optional
SDK and checks Boat/public webhook imports and types under NodeNext. Its fake
transport never calls Boat. `pnpm test:release` checks candidate metadata and
artifact/output boundaries. Full `pnpm check:all` runs these gates on UbiCloud;
verify the actual runner identity, not only a configured runner label.

Preparing a candidate changes no publication or credential settings. Do not
remove `private: true`, change registry access, run npm publish, install guest
runtimes, mount external storage, or add consumer desktop/profile behavior as part
of this handoff. Those are separate scopes.
