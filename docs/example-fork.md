# Stopped-source forks

Forks creates a billable machine and requires the existing finite run approval.
Planning and this implementation do not authorize a live fork. Open Forks from
source details, choose a distinct unused child key, and review the selected pair.
The URL preserves both keys. Each child key has one immutable host intent and
shared allowance reservation. Create and fork reservations cannot claim the same
logical key, even before a native reference is known.

Prepare the source's retained home fixture in its lifecycle panel while running.
Complete its nonforced stop and inspect the original shared job until the
component confirms stopped state. Fork admission rejects a pending stop, an active
operation, an unprepared fixture or a mismatched binding. It reads the stopped
source's exact fixture bytes before admission. Running forks can omit recent
writes, and `/tmp` is excluded from snapshots. No saved snapshot/capture substitute
or shell fallback is used.

The host checks verified operator scope, the original reviewed account and active
run duration, then atomically reserves the child intent, allowance and shared source image
operation alongside the completed-stop check. A resume cannot slip between that
check and the native dispatch. The preflight fixture read is fenced to that same
source version and completed-stop identity, so a changed stopped epoch must be
reviewed again before admission. The public shared image client claims the reserved
operation before its native fork. It uses private/no-inherited-environment defaults. If a concurrent lifecycle operation wins before admission, the whole transaction
refuses without retaining a new fork intent or allowance reservation.

A verified native acknowledgement stores its readiness handle and optional
`nativeImage.acceptedMachine` in the shared operation before another read. The
app explicitly authorizes and registers that accepted reference under the new
child key, including while readiness is pending. It never decodes opaque handles
to guess IDs and never rebinds the source. Later readiness must match the same
accepted child. The optional field preserves existing providers that return only
a pending job handle or an immediate ready result.

Inspect original fork performs a bounded shared status read. The initial 202 does
not prove readiness. Verify retained copy is enabled only after the original fork
reports ready. It refreshes the child through the public lifecycle client, waits
for native running observation and reads the exact fixture path through the public
file client. It compares every byte to the original fixture and records matched
or mismatch only against the same child binding. If guest files are not ready,
verification stays unconfirmed and can be inspected again without another fork.

A lost reply, including a conflict without a child ID, leaves an unresolved
intent and reservation. Reopening or repeating start returns that intent and
never sends another POST. A missing accepted reference does not prove no stopped
child exists. Recovery does not scan the account, guess IDs, reset journals or
release uncertain allowance. A pre-dispatch crash window may also leave a counted
intent without a shared operation; keep that original intent. No support contact
or new native mutation is authorized by this workflow.

Accepted children use their own existing lifecycle and exact-owned cleanup pages.
A separately confirmed exact-owned child stop releases fork concurrency once,
without resetting cumulative machine, start or dollar reservations. The parent
remains stopped until an explicit approved resume through its existing workflow.
The earlier real fork HTTP409 remains unresolved; these offline tests do not
change that outcome or qualify provider-wide support.

Ordinary backend tests use synthetic native HTTP and the actual shared component
stores. Browser tests exercise the production panel with labeled synthetic state.
They verify stop refusal, distinct IDs, retained intents and copy/mismatch states,
not a live hosted session. Local development stays on isolated anonymous managed
backends. Hosted configuration must verify the actual FantasticDev team slug/ID,
reuse the correct existing project and verify the selected deployment. No hosted
production deployment, Boat provisioning or package publication is authorized.
